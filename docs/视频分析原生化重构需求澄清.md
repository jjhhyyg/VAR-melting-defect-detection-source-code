# 视频分析重构需求澄清

> 状态：关键技术路线已重新排序。当前优先目标是先把分析链路从 tracking 改为 YOLO-only detect-only；ONNX Runtime 和预处理 GPU 加速都后置为优化项。当前处于 Phase 0，已准备 `golden_samples`，放于 `./golden_samples` 中，本文档保留为后续原生化重构依据。

## 现状摘要

当前桌面分析链路仍以 Python worker 为核心：

- `ai-processor/desktop_worker.py` 读取 Rust 写入的 job JSON，通过 stdout NDJSON 回传进度、结果、模型版本和视频产物路径。
- `ai-processor/preprocessor/video_preprocessor.py` 使用 Python OpenCV CPU 逐帧预处理。
- `ai-processor/analyzer/yolo_tracker.py` 使用 Ultralytics YOLO 的 `model.track(...)`，底层包含 BoT-SORT 追踪。
- `ai-processor/analyzer/video_processor.py` 先预处理，再逐帧检测/追踪，记录轨迹、动态指标，之后基于 `trackingObjects` 生成 `anomalyEvents`。
- `frontend/src-tauri/src/lib.rs` 的 SQLite schema 和结果接口仍包含 `enable_tracking_merge`、`tracking_merge_strategy`、`tracking_objects`、`trajectory_json`、`object_id` 等现有追踪字段。
- `frontend/app/pages/index.vue` 和 `frontend/app/pages/tasks/[id].vue` 仍展示“追踪轨迹合并”和“轨迹查看”。

本次重构不是小改。第一阶段先收敛事件语义、数据库 schema、前端结果展示和报告字段；推理运行时切换到 ONNX、预处理 GPU 化、Windows 发布优化都放到后续阶段。

## 当前确认目标

### 1. 预处理

- 第一阶段保持现有 Python OpenCV CPU 预处理，不把预处理 GPU 化纳入当前改造。
- 不在第一版做 C++ OpenCV、OpenCV CUDA、NVDEC/NVENC 或自定义 CUDA kernel。
- 预处理平均 FPS 仍需统计并写入结果。
- 预处理关闭时，`preprocessingAverageFps` 返回 `null`。

判断：预处理 GPU 化会把 OpenCV CUDA、视频编解码和 Windows DLL 打包复杂度一次性拉满，但当前更重要的是先解除追踪耦合，把 YOLO-only 事件链路跑通。预处理 GPU 化应最后再评估。

### 2. 缺陷检测

- 不再使用目标追踪模型，仅使用 YOLO 检测。
- 第一阶段先沿用现有 `.pt + Ultralytics/PyTorch` 生态，只把 `model.track(...)` 改为 detect-only。
- Windows 当前作为主要验证平台，优先完成 `.pt` detect-only 闭环。
- macOS 后续同步 `.pt + MPS/CPU` detect-only 路线。
- ONNX Runtime 不进入第一阶段，等 YOLO-only 语义、schema、前端展示稳定后再单独优化。
- 后续如果引入 `.onnx`，必须用 golden sample 做 `.pt` 与 `.onnx` 输出一致性验收，不能默认两边输出完全一致。

判断：这次顺序应先改语义，再改运行时。先用现有 `.pt + Ultralytics/PyTorch` 把追踪耦合拆掉，能更快验证缺陷事件是否正确；ONNX Runtime 属于后续性能和发布优化，不应成为 YOLO-only 重构的前置条件。

### 3. 缺陷事件

- 缺陷类别限定为六类（与 `best.pt` 的 `model.names` 一致）：
  - 0 → 熔池未到边 → `POOL_NOT_REACHED`
  - 1 → 电极粘连物 → `ADHESION`
  - 2 → 锭冠 → `CROWN`
  - 3 → 辉光 → `GLOW`
  - 4 → 边弧（侧弧） → `SIDE_ARC`
  - 5 → 爬弧 → `CREEPING_ARC`
- 帧号统一采用 0-based frame index：第一帧为 `0`，最后一帧为 `totalFrames - 1`。
- 检测到某类别缺陷的证据帧后，该帧前后各 1 秒都算作该类别缺陷出现时间段，注意计算后不能超过视频开头和结尾的边界。
- 前后 1 秒按源视频 FPS 计算。
- 只合并同类别内部重叠或相邻区间。
- 不同类别时间段即使重叠，也保留为独立事件。
- “掉入熔池”判断不再保留。
- 旧追踪相关字段从代码、接口和数据库中删除，不保留旧任务兼容。

### 4. 输出结果

视频分析结果需要给出：

- 视频帧率。
- 预处理平均 FPS。
- 缺陷检测平均 FPS。
- 动态指标第一阶段暂不改动，继续沿用当前输出；后续再评估是否增加每类缺陷逐帧数量、最大置信度、框面积占比等 YOLO-only 指标。
- 带框结果视频，需要导出；只展示缺陷种类，不再绘制 track ID。

## YOLO-only 后处理算法

输入：逐帧 YOLO 检测结果、`sourceVideoFps`、`totalFrames`、缺陷类别集合。

1. 遍历每帧检测结果。
2. 仅保留六类缺陷：熔池未到边、电极粘连物、锭冠、辉光、边弧（侧弧）、爬弧。
3. 按缺陷类别分别收集证据帧。若某帧存在该类别检测框且置信度达到阈值，则该帧成为该类别的证据帧。
4. 对每个类别的每个证据帧 `f` 生成区间。帧号统一采用 0-based frame index：
   - `radius = round(sourceVideoFps * 1.0)`
   - `startFrame = max(0, f - radius)`
   - `endFrame = min(totalFrames - 1, f + radius)`
5. 在同类别内按 `startFrame` 排序。
6. 仅合并同类别内重叠或相邻区间，即 `next.start <= current.end + 1`。
7. 合并时聚合：
   - 最高置信度。
   - 证据帧列表或证据帧数量。
8. 输出 `anomalyEvents`，`eventType` 按缺陷类别区分。

不同类别之间不合并。前端展示时按类别泳道分层，允许同一时间横坐标上出现多个类别事件。

## 预处理 GPU 化暂缓说明

第一版 macOS/Windows 都继续使用 Python OpenCV CPU。OpenCV CUDA 和 C++ OpenCV 不进入当前实现范围。

如果后续重新启动预处理 GPU 化，当前 Python CPU 算法的初步评估如下：

| 当前步骤 | CPU 实现 | OpenCV CUDA 可行性 | 是否可严格留在 GPU |
| --- | --- | --- | --- |
| 强/中去噪 | `cv2.bilateralFilter` | `cv::cuda::bilateralFilter` 可覆盖 | 可以 |
| 轻度去噪 | `cv2.medianBlur` | `cv::cuda::createMedianFilter` 可覆盖 | 可以 |
| 色彩空间转换 | `cv2.cvtColor` | `cv::cuda::cvtColor` 可覆盖 | 可以 |
| 通道拆分/合并 | `cv2.split/merge` | CUDA split/merge 或 mixChannels 路径可覆盖 | 可以 |
| 自适应 gamma 均值判断 | `np.mean(y)` 后在 CPU 决定 gamma | OpenCV CUDA 可做部分 reduction | 纯 OpenCV CUDA 不理想；要严格不回 CPU，建议自定义 CUDA kernel |
| gamma LUT | `cv2.LUT` | CUDA LUT/LookUpTable 路径可实现 | 可以，但需结合 gamma 选择 |
| HSV 阈值 mask | `cv2.inRange`、`bitwise_and` | CUDA arithmetic/imgproc 可覆盖 | 可以 |
| 形态学开运算 | `cv2.morphologyEx(..., MORPH_OPEN)` | CUDA morphology filter 可覆盖 | 可以 |
| mask 高斯模糊 | `cv2.GaussianBlur` | CUDA Gaussian filter 可覆盖 | 可以 |
| 亮度通道增强 | `cv2.convertScaleAbs` | 可用 CUDA arithmetic 或自定义 kernel | 可以 |
| 按 mask 混合 V 通道 | `v * (1 - mask) + v_enhanced * mask` | `cv::cuda::blendLinear` 或自定义 kernel 可实现 | 建议自定义 CUDA kernel，最稳 |
| 最终原图/处理图加权融合 | `cv2.addWeighted` | CUDA arithmetic 可覆盖 | 可以 |

结论：

- 大多数现有 CPU 算子可以映射到 OpenCV CUDA。
- 要严格做到“只有输入/输出才用 CPU”，最麻烦的是自适应 gamma 均值分支和熔池增强的 mask 浮点混合。
- 视频解码/编码默认仍是 CPU `VideoCapture/VideoWriter`。若后续要求 NVDEC/NVENC，是另一层需求，不应和本次检测重构混在一起。

## 推荐架构

```text
Tauri Rust app
  └── analysis worker protocol: job JSON + stdout NDJSON
        ├── Preprocessing: Python OpenCV CPU
        ├── Windows detector first: .pt + PyTorch/Ultralytics detect-only
        ├── macOS detector later: .pt + PyTorch/Ultralytics detect-only + MPS/CPU fallback
        ├── YOLO-only event interval merger
        ├── dynamic metrics calculator
        └── annotated video exporter
```

后续优化阶段再评估 Windows ONNX Runtime + CUDA EP，不作为第一阶段架构前提。

协议层建议继续保留当前 job JSON + stdout NDJSON：

- 当前 Rust 侧已有 `WorkerEvent`、`ProgressPayload`、`ResultPayload` 处理逻辑。
- 可以减少调度器和 Tauri 桥接层的改动。
- 关键变化在 payload 字段和数据库 schema，而不是 IPC 形式。

## 阶段拆分建议

### Phase 0：冻结契约

- 确认缺陷类别集合、事件合并规则、结果字段。
- 使用现有 `golden_samples` 冻结 YOLO-only 事件验收口径。
- 明确 Windows Phase 0 采用 0-based frame index。
- 明确新数据库 schema，删除追踪字段，不做旧任务兼容。
- 动态指标第一阶段暂不改动。
- 不在 Phase 0 固定 Windows ONNX 导出参数。

### Phase 1：Windows YOLO-only 快速闭环

- 保留 Python OpenCV CPU 预处理。
- 将 Ultralytics `model.track(...)` 改为 detect-only。
- Windows 先沿用现有 `.pt + Ultralytics/PyTorch` 运行时。
- 实现 YOLO-only 事件区间生成和同类别合并。
- 用 `golden_samples` 验收 Windows 输出。
- 导出无 track ID 的结果视频。

### Phase 2：删除追踪语义和前端旧展示

- 删除前端轨迹合并配置、追踪对象列表、轨迹查看和 `objectId` 展示。
- 删除数据库追踪字段并初始化新 schema。
- 删除接口里的 `trackingObjects`、`objectId`、`trajectory_json`。
- 保留动态指标当前输出，不把它和 tracking 绑定。

### Phase 3：macOS detect-only 同步

- macOS 继续使用 `.pt + PyTorch/Ultralytics detect-only`。
- 推理优先 MPS，必要时 CPU。
- 使用同一组 golden samples 对齐事件语义。

### Phase 4：Windows ONNX Runtime 优化候选

- 等 YOLO-only 语义、schema 和前端展示稳定后，再从同一训练产物导出 ONNX。
- 单独固定 ONNX opset、输入尺寸、NMS 位置和类别映射。
- 接入 ONNX Runtime CUDA EP。
- 使用 golden samples 对比 Windows `.pt` 与 Windows `.onnx` 的缺陷事件输出。
- 写入 `detectionBackend`、检测 FPS、设备信息。

### Phase 5：Windows 发布与 CUDA 验证

- Windows x64 构建由 Windows 构建机产出。
- 固定 ONNX Runtime、CUDA、cuDNN、显卡驱动最低版本。
- 目标 GPU：RTX 3090 / RTX 4090。
- CUDA 版本在 12.6 / 12.8 中二选一，不能两个都作为发布基线。
- 验证无 NVIDIA GPU、驱动过旧、CUDA 初始化失败、显存不足、ONNX Runtime GPU EP 初始化失败等场景。

### Phase 6：后续预处理加速候选

- 只有当检测侧已经稳定，且预处理成为瓶颈时，再评估 C++ OpenCV / OpenCV CUDA / NVDEC / NVENC。
- 不要在当前阶段把预处理 GPU 化和检测推理重构绑死。

## 当前不建议直接做的事

- 不建议在第一阶段引入 ONNX Runtime；先把 YOLO-only 语义重构做完。
- 不建议继续追求“全平台同一推理栈”；先沿用 `.pt + Ultralytics/PyTorch` 完成 detect-only 闭环。
- 不建议在 macOS 上强行走 ONNX Runtime CPU EP 或 CoreML EP；macOS 后续仍走 MPS + `.pt`。
- 不建议在第一版做 C++ OpenCV 或 OpenCV CUDA 预处理。
- 不建议把 `.pt` 与 `.onnx` 输出一致性当作理所当然；等 ONNX 阶段启动后，必须用 golden sample 验收。
- 不建议保留 `objectId`、`trackingObjects`、`trajectory_json` 等旧字段；本系统按全新 schema 处理。
- 不建议在 macOS 本机承诺产出 Windows x64 CUDA 安装包。
